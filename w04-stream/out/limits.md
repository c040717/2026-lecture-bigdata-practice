# Task 2 메모리 실험

## 환경과 측정 방법

2026년 10월 7일, Intel i7-1165G7, 약 16 GB RAM(15.68 GiB), Windows 11, Python 3.12.6에서 측정했다. Whale 브라우저, Windows Defender와 일반 백그라운드 프로그램이 실행 중이었다. 측정 중 브라우저로 저장소 작업도 진행했으므로 다른 프로그램을 모두 끈 환경은 아니다.

스트림 크기는 4가지이고 100,000~6,400,000개로 64배 범위다. seed는 246이며 원래 제공된 stream 함수를 그대로 사용했다. 같은 seed와 길이로 정확한 집합과 FM을 각각 한 번씩 실행했다. 스트림 전체를 리스트로 만들지 않고 원소를 하나씩 읽었다.

FM은 이 실험에서 해시 개수를 32개로 고정했다. Task 1 구현의 기본값은 64개이며, Task 2에서는 처리 비용을 줄이기 위해 32개를 선택했다. 모든 크기에 같은 개수를 적용했다.

시간과 메모리는 두 방법의 전체 실행을 tracemalloc으로 측정했다. 데이터 생성도 이 실행 안에 포함된다. 메모리 값은 실행 중 추가 할당량의 최댓값이며 Python 전체나 시스템 전체 메모리가 아니다. 시간에는 메모리 추적 비용도 포함된다.

## 메모리 증가율

| 크기 변화 | 길이 증가율 | 집합 메모리 증가율 | FM 메모리 증가율 |
|---|---:|---:|---:|
| 100,000 → 400,000 | 4배 | 2.953배 | 1.0001배 |
| 400,000 → 1,600,000 | 4배 | 4.024배 | 1.0000배 |
| 1,600,000 → 6,400,000 | 4배 | 4.036배 | 1.0001배 |

처음과 마지막을 비교하면 집합은 3,925,612→188,287,586바이트로 47.96배 늘었다. 길이 64배에 대해 log(47.9639)/log(64)≈0.93이므로 대략 n^0.93 증가였다. 서로 다른 원소가 늘어날수록 저장할 문자열과 집합 공간이 늘었다. 집합은 크기가 바뀔 때 저장 공간을 한꺼번에 늘리므로 매 구간의 비율이 정확히 같지는 않았다.

FM은 7,974→7,976바이트로 1.0003배였고, 같은 계산에서 지수는 0.0001였다. 이 범위에서는 약 7.79 KiB로 거의 일정했다. 저장하는 최댓값은 해시 개수 32개로 정해지며, 입력 길이에 비례한 집합을 저장하지 않는다.

## 정확도와 시간의 대가

추정/실제 비율은 0.670~0.892였다. 상대 오차는 처음 33.0%, 마지막 10.8%로 줄었다. 해시 개수를 고정했기 때문에 입력 길이를 늘리는 것만으로 오차가 사라지지는 않는다. 해시 결과의 우연성과 제한된 추정값 개수 때문에 편차가 남는다.

이번 구현에서는 FM이 집합보다 느렸다. 원소마다 32개의 해시값과 최댓값을 확인하는 작업이 필요하고 메모리 추적도 실행 시간을 늘렸다. FM의 장점은 이 실험에서 속도가 아니라 작은 저장 공간이었다.

## 오래 기다리게 된 크기

스트림 6,400,000개에서 집합 계산은 63.65초로 1분을 넘었다. 집합의 최대 추가 할당량은 188.29 MB(179.57 MiB)였다. 메모리 부족 오류는 없었으며 기다리는 시간 때문에 이 크기에서 증가 실험을 멈췄다. PC의 메모리 한계에 도달했다고 주장하는 것은 아니다.

두 배 정도의 오차는 방문자 규모나 증가 추세를 대략 파악하는 용도에는 받아들일 수 있다. 방문자 수에 따라 요금을 청구하거나 정확한 수치를 보고해야 할 때에는 적합하지 않다.
