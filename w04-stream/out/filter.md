# 필터의 해시 수와 메모리 예산

## 해시 수 계산

비트 수를 m, 삽입 수를 n, 해시 수를 k라고 하면 예상 오탐률은 다음과 같다.

```text
p(k) = (1 - exp(-kn/m))^k
ln p(k) = k ln(1 - exp(-kn/m))
```

a=n/m으로 두고 미분하면 다음과 같다.

```text
d(ln p)/dk = ln(1-exp(-ak)) + ak exp(-ak)/(1-exp(-ak))
```

exp(-ak)=1/2일 때 오른쪽은 -ln(2)+ak=0이므로 k=(m/n)ln(2)이다. m/n=10이면 k≈6.931이고 정수로 7을 선택했다.

이론적인 최소율은 exp(-10*ln(2)^2)≈0.8193%다. 실험에서는 1,785/200,000=0.8925%였으며 거짓 음성은 0개였다. 기준 필터는 19,023/200,000=9.5115%이므로 오탐을 약 90.62% 줄였다.

## 실제 저장 공간

비트마다 바이트 하나를 쓰지 않고 bytearray 안에서 비트를 묶어 저장했다. __slots__를 사용해 인스턴스의 별도 속성 딕셔너리도 없앴다. 이 Python 환경에서 공간은 다음과 같다.

| 저장 대상 | 바이트 |
|---|---:|
| 필터 인스턴스 | 48 |
| seed 정수 | 28 |
| bytearray 관리 공간 | 57 |
| 비트 배열 데이터 | 9,867 |
| 합계 | 10,000 |

memory_bits()는 sys.getsizeof로 필터 인스턴스, seed와 bytearray의 크기를 합산해 80,000비트를 반환한다. 공유하는 Python 코드나 조회 도중 잠시 생성되는 값까지 포함한 프로세스 전체 메모리 측정은 아니다. 필터가 유지하는 공간을 센다.

관리 공간 때문에 실제 조회에 사용하는 비트 배열은 78,936비트다. 따라서 원소당 배열 비트 수는 9.867이고 k=7의 예상률은 (1-exp(-7*8000/78936))^7≈0.8740%다. 실측 0.8925%는 이상적인 10비트의 0.8193%보다 약 0.073퍼센트포인트 높았다. 유한한 조회 표본과 관리 공간의 차이가 있으며 이론보다 좋다고 주장하지 않는다.

## 삽입 개수를 모를 때

예상 삽입 수로 초기 크기를 정하고 비트가 얼마나 찼는지 확인한다. 메모리가 더 허용되면 기존 필터를 그대로 유지하면서 새 필터를 추가하고, 조회할 때 기존 필터도 함께 확인할 수 있다. 고정된 예산에서 원소가 계속 늘면 오탐률 증가를 피할 수 없다.

삽입 수를 너무 작게 예상하면 비트가 빨리 차서 오탐이 많아지고, 너무 크게 예상하면 불필요하게 많은 비트 공간을 확보한다. 과거 원소의 비트를 임의로 지우면 거짓 음성이 생길 수 있으므로 삭제해서 해결하지 않는다.
